Week 4: Server clone, backups and database replication

1. Server A counter page

http://195.148.21.71/viikko2/ (primary; this page increases the counter on every load)

2. Server B counter page

http://128.214.254.158/viikko4/ (replica, read-only; loading it never changes the counter)

3. How Server B was created

Server A was cloned with a cPouta snapshot (linux_wille, 80 GB). A new instance, linux-ville-b, was launched from the snapshot with flavor standard.large. B got its own floating IP, 128.214.254.158. After launch, B's MariaDB server_id was changed to 2 and Nginx was restricted so that B serves only /viikko4/.

4. Disk layout

Server B has one 80 GB root filesystem (/), about 5 % used. There are no separate data volumes. Backups are stored under /var/backups/viikko4/ on the same disk.

5. Backup location

/var/backups/viikko4/ on Server B. It is outside the web root, so it cannot be reached through a browser. Each run creates its own timestamped directory, for example 2026-11-19_17-00, so old versions are not overwritten. The directory names use the server's UTC time (YYYY-MM-DD_HH-MM), which is two hours behind Finnish winter time: the run 2026-11-19_17-00 was made on 19.11.2026 at 19:00 Finnish time.

6. Linux users

  • ubuntu: login user and owner of the application.
  • root: runs the backup cron job and holds the synchronisation key.

7. Database users

  • viikko2app (localhost): the application user. It has only SELECT, UPDATE on viikko2.laskuri.
  • replicator (from 192.168.1.240): replication user on Server A with only the REPLICATION SLAVE privilege. It also exists on B because it arrived with the snapshot data, but B does not use it.
  • root, mysql, mariadb.sys: MariaDB system accounts.

8. Ownership

  • /var/backups/viikko4/: root:root
  • /root/.ssh/sync_ed25519: root, private key, never published
  • /var/www/html/Linux: ubuntu:ubuntu (mode 755)

9. Permissions

  • /var/backups/viikko4/ is mode 700, so only root can read it.
  • On Server A, the synchronisation key in authorized_keys is restricted with from="192.168.1.240", so it works only from Server B.
  • MariaDB port 3306 is open in the security group only to 192.168.1.240/32. It is not open to the internet.
  • B's database is read_only = ON, so ordinary users cannot write to it.

10. Cron schedule

Root's crontab on B runs once an hour:

0 * * * * flock -n /run/www-sync.lock rsync -a -e "ssh -i /root/.ssh/sync_ed25519 -o BatchMode=yes" ubuntu@192.168.1.157:/var/www/html/ /var/backups/viikko4/$(date +\%F_\%H-\%M)/ >> /var/log/www-sync.log 2>&1

B pulls the files from A over the internal network. flock prevents overlapping runs. The server clock is UTC, so the job runs at every full hour in UTC, which is two hours later on the Finnish clock (for example 18:00 UTC = 20:00 Finnish time).

11. MariaDB replication

A is the primary (server_id = 1, binary log, ROW format) and B is the replica (server_id = 2, read_only = ON, event_scheduler = OFF). An initial mariadb-dump with --master-data=2 was loaded onto B, replication was started from the recorded binlog position, and the dump files were deleted afterwards. SHOW REPLICA STATUS shows Slave_IO_Running: Yes, Slave_SQL_Running: Yes and 0 seconds behind. Replication is not a backup, because deletions replicate too. That is why the hourly file copies exist.

12. Test results

  • Ping between A and B: 0 % packet loss.
  • Replication: the counter moved from A to B (224 → 228 → 230 → 231).
  • Loading B's /viikko4/ three times did not change the counter (230 before and after).
  • B's /viikko2/ fails, because B is read-only and cannot execute the counter's UPDATE.
  • B returns 404 for every path except /viikko4/.
  • Cron made 22 consecutive hourly copies (18.11.2026 at 22:00 – 19.11.2026 at 19:00 Finnish time) with no errors in the log.

13. Restore test

The file index.nginx-debian.html was copied from /var/backups/viikko4/2026-11-18_19-31/ to /tmp/palautustesti/ on 18.11.2026 at about 21:35. The SHA-256 of the restored file matched the original on Server A (fb47468a…d6de).

14. Reboot test

B was rebooted on 19.11.2026 at 20:00:45 and was back at 20:02:44 (Finnish time). Nginx, MariaDB, the application service and cron were all active, replication was Yes/Yes with 0 seconds lag, and /viikko4/ returned 200. After the reboot, cron kept running: the backup directory 2026-11-19_19-00 (UTC) was created automatically at 21:00 Finnish time, with no errors in the log.

15. Problem solved

After cloning, B served the whole website, because Nginx's location / proxied everything to Flask. Opening B's /viikko2/ also failed, because the page tries to increase the counter while B is read-only. I fixed both. A separate read-only route /viikko4/ only runs a SELECT, and Nginx on B now returns 404 for every other path. I learned that a clone inherits everything from the original and needs to be trimmed to its real role.
